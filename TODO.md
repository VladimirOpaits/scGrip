## Адаптеры на замороженном backbone (пивот 2026-09-09, см. CLAUDE.md)

Новая основная линия метода (не отменяет EWC-baseline ниже — та секция закрыта и остаётся
как сравнение). Backbone = наша собственная `models/census_base/scvi_census_healthy_base`
(1605 доноров, проверено — ни lupus, ни RA атлас туда не попали). Публичная CZ Census
модель (`models/census_scvi_public/model.pt`) НЕ используется как backbone (contamination —
lupus и RA оба уже внутри Census, см. CLAUDE.md).

Порядок реализации (ничего из этого ещё не начато кодом):

1. **Adapter-модуль**: `down: Linear(n_hidden→r) → nonlinearity → up: Linear(r→n_hidden)`,
   `up` веса и bias — нулевая инициализация (verify: выход модели bit-identical до первого
   шага оптимизации, тот же паттерн проверки, что в `verify_identical()` из
   `build/finetune_anchored_depthcov.py`). Вставка точки — ПОСЛЕ каждого скрытого блока
   `z_encoder.encoder.fc_layers[i]` (i=0,1; n_hidden=128) И decoder `px_decoder.fc_layers[i]`,
   backbone заморожен целиком (`requires_grad=False` на всех исходных параметрах,
   `module.eval()`-режим для BatchNorm running stats — не train mode).
2. **Anchor-на-адаптере**: `λ·mean(‖adapter_out‖²)`, считается ТОЛЬКО на здоровых клетках
   новой когорты (lupus: `cohort2_normal`; RA: RA-normal донорах) — НЕ на replay census
   (в отличие от старого anchor, здесь census-клетки вообще не должны идти через forward
   с адаптером, т.к. backbone для них уже точен по построению).
3. ELBO считается на ВСЕХ клетках новой когорты (healthy + disease) как обычно — это то,
   что даёт адаптеру стимул использовать свободу на больных клетках для честной
   реконструкции, а не просто занулиться везде.
4. Depth-covariate (для RA, где нужен) — переносится с decoder-хирургии
   (`finetune_anchored_depthcov.py`) на вход адаптера: `down(concat(h, depth_z))`, а не
   отдельная хирургия decoder — тот же принцип (дать модели прямой доступ к технической
   переменной), но единым механизмом для энкодера и декодера через один и тот же адаптер.
5. Порядок тестирования: **lupus cohort2 первым** (основной кейс, уже есть весь остальной
   пайплайн — `paper/{encode,geometry,conservation}.py`), **RA вторым** как независимая
   репликация (данные и padding-фикс уже готовы, `build/ra_base.py`).
6. Repulsion/margin-term для SLE/RA-клеток — ТОЛЬКО после того как attract-only (anchor-
   на-адаптере) версия сойдётся и даст разумную геометрию. Формула (обсуждена, не
   реализована): `L_repel = relu(m_healthy − MMD_strat(z_disease, z_healthy_ref))`, где
   `m_healthy` — тот же stratified MMD, посчитанный между двумя независимыми ЗДОРОВЫМИ
   когортами (напр. census vs cohort2_normal) — калиброванный, а не произвольный порог.
7. Отложено, не блокер: Sade-Feldman (`data/sade_feldman/`, GSE120575, T-cell exhaustion,
   вне Census) — нужна отдельная scVI-база под Smart-seq2/TPM, не наш 10x census-encoder;
   Down-syndrome/trisomy-21 — не нашли открытый adult-PBMC 10x accession, вернуться если
   найдётся конкретная ссылка.

## EWC baseline (пивот 2026-09-07, см. CLAUDE.md)

Первая статья теперь про метод (anchor + stratified MMD), с EWC как внешним
baseline-сравнением. Код: `build/finetune_ewc.py` (Fisher-diagonal penalty к параметрам,
--lam-anchor=0 для чистого EWC, >0 для EWC+anchor), отчёт — `scenarios/EWC_test.py`.
Последовательность (согласована с Владом): сначала EWC-only, только если он выглядит
конкурентным с чистым anchor — комбинировать лоссы в EWC+anchor.

### СДЕЛАНО 2026-09-07: EWC-only свип по λ (1e7/1e8/1e9/1e10) — плохо и НЕ реагирует на λ

Подробности в памяти `ewc-fisher-decoder-dilution`. Числа идентичны на всех 4 порядках λ
и хуже anchor на каждой оси (`census_CV` 0.406 vs 0.279, `block_offset` 1.098 vs 0.971,
`gap_sigma` 1.80 vs 2.52, `AUC_sle_vs_norm` 0.857 vs 0.909). Вероятный механизм — виден
прямо в логе: топ-5 параметров по Fisher — все из `decoder.px_decoder.fc_layers`
(Fisher ~22–28), первый ЭНКОДЕРНЫЙ параметр (`z_encoder.mean_encoder.bias`) только
пятый (~16). EWC-штраф суммируется по ВСЕМ параметрам — раз decoder систематически
имеет больший Fisher, штраф в основном защищает decoder (реконструкцию), а не encoder
(латентную геометрию, которую мы измеряем). Anchor, наоборот, бьёт по `qz.loc`
напрямую. Поэтому рост λ на 3 порядка ничего не поменял — менялась общая величина
штрафа, а не его распределение encoder/decoder.

**Следующий шаг, если EWC продолжать как baseline** (не начато): ограничить сумму
штрафа ТОЛЬКО на `z_encoder.*`-параметрах — прямая проверка механизма. Если и это не
помогает — EWC как честный внешний baseline проигрывает anchor'у, и это ЧЕСТНЫЙ
негативный результат для статьи (task-specific анкер бьёт глобальную
parameter-регуляризацию), а не повод для дальнейшего тюнинга λ.

### СДЕЛАНО 2026-09-07: EWC+anchor комбинация — НЕ лучше чистого anchor

Подробности — память `ewc-anchor-combo-and-donorfrac5`. `--lam-ewc 1e8 --lam-anchor 30`:
`census_CV`/`block_asw` возвращаются к уровню чистого anchor (anchor-часть лосса
доминирует), но `block_offset` (сырое расстояние центроидов) СТАНОВИТСЯ ХУЖЕ и
anchor'а, и даже EWC-only (1.326 vs 0.971 vs 1.098) — лоссы не складываются чисто,
похоже на то же трение, что уже предполагалось для EWC+MMD, только тут между EWC и
anchor/ELBO. Комбинацию дальше без новой идеи не гонять — `final` (anchor+MMD)
остаётся лучшей аркой практически по всем метрикам.

Заодно проверил scIB: `scib_bio` (donor-ASW) плоский на ВСЕХ 11 протестированных
арках (~0.49/~0.876) — ожидаемо, эта метрика по конструкции слепа к нашему
батч-эффекту (см. докстринг `paper/conservation.py`). Информативная версия —
`block_asw` (census-vs-cohort silhouette по компартментам), использовать её, не
`scib_bio`, если нужен scIB-номер для сравнения методов.

### СДЕЛАНО 2026-09-08: почему у CLCVAE EWC «работает», а у нас нет — прочитал статью целиком

Память `clcvae-ewc-precedent` — полный разбор. Коротко: у CLCVAE conditional-энкодер,
и их EWC штрафует только общий backbone, а под НОВЫЙ батч заводятся отдельные
conditional-веса (Fisher=0, вообще не участвуют в штрафе) — то есть EWC решает
лёгкую задачу («чуть подвинь backbone», основную работу поглощает выделенный карман
параметров). У нас `encode_covariates=False` — такого кармана нет вообще, всё
дообучение идёт через ОДНИ И ТЕ ЖЕ веса, которые EWC одновременно пытается удержать.
Это структурно объясняет и разбавление Fisher по decoder (выше), и общий проигрыш —
не вопрос неправильной λ. Плюс даже в самой статье выигрыш EWC — «marginally better»
чем просто заморозка, и никогда не сравнивался ни с чем похожим на наш anchor.

**Вывод: дальше тюнить λ или комбинации бессмысленно.** Честная воспроизводимая
версия их метода потребовала бы завести настоящие conditional/батч-веса в энкодере
(отказ от `encode_covariates=False`) — это архитектурное изменение, а не
гиперпараметр. Encoder-only Fisher (см. пункт выше) — не то же самое, что их
разделение, но ближайшее, что можно попробовать без смены архитектуры; если и это
не поможет — фиксировать как честный отрицательный результат для статьи.

**Диагностика для слайдов (обсуждено 2026-09-07, не начато).** Для EWC+anchor+MMD прогона
сохранять на промежуточных чекпойнтах (не только на финальном) латентные координаты
репрезентативной выборки клеток — census-реплей (та же фиксированная выборка, что уже
используется как якорь/Fisher-набор, чтобы координаты были сравнимы между чекпойнтами по
ОДНИМ И ТЕМ ЖЕ клеткам) + группы A/B когорты (те, что участвуют в стратифицированном MMD)
+ ОТДЕЛЬНО проекции больных доноров (SLE), которые НИКОГДА не входят ни в один лосс —
их движение по чекпойнтам чисто иллюстративное, не может быть артефактом переобучения на
метку. По этим координатам — UMAP на каждом чекпойнте (одна и та же обученная UMAP-модель
или хотя бы общий сид/параметры, иначе кластеры "плывут" сами по себе и это будет читаться
как ложный сигнал движения). Цель — слайды, показывающие (1) как сохраняется форма
референсного облака (census) во времени, (2) как группа B стратифицированного MMD сходится
к référence по компартментам, (3) как больные (не участвующие в обучении) ведут себя
относительно здоровых — чисто описательно, не как метрика приёмки.

Практически: в `finetune_ewc.py`/`finetune_mmd_stratified.py` на каждый `check_every`/
milestone шаг помимо чисел печатать/сохранять `z = encode(fixed_rows)` в маленький
`.npz` (индексы `fixed_rows` фиксированы один раз в начале прогона — census-реплей +
donor-stratified подвыборка A/B + все SLE-строки query, ~несколько тысяч клеток, не всё
облако). Отдельный скрипт `scenarios/checkpoint_umap.py` (пока не написан) читает эти
`.npz` по всем чекпойнтам одного прогона и рисует общую UMAP-проекцию (fit один раз на
объединении всех чекпойнтов, transform каждого чекпойнта в неё, а не пересчитывать UMAP
заново на каждом — иначе оси между кадрами не сопоставимы).

**Вопрос.** Сейчас якорь берёт ВСЕХ 1605 доноров census по 25 клеток (~40k) — это
выбрано как «все», без обоснования. Сколько на самом деле нужно, и что важнее:
число доноров или глубина на донора?

**Почему это не праздный вопрос.** Реплей-клетки идут только через энкодер, а энкодер
при `encode_covariates=False` батч-слепой — значит `donor_id` для якоря не батч-левел,
а просто схема стратификации покрытия многообразия экспрессии. Плюс held/replay ratio
1.04–1.12 говорит, что мы, вероятно, глубоко в насыщении.

**Дизайн.** Фиксировать бюджет, менять форму (`sceris.anchor.replay_index` уже разводит
две оси, донорские подмножества вложены):

| бюджет | формы (доноров × клеток) |
|---|---|
| 10k | 400×25, 1000×10, 100×100 |
| 5k  | 200×25, 1000×5, 50×100 |
| 2k  | 80×25, 400×5, 20×100 |

Свипать только phase 1 (ELBO на нормальных когорты + якорь), без MMD — иначе MMD
замажет эффект.

**Метрики** (те же, что уже в статье): `census_pairwise_CV`, `ref_mean`, block offset,
held/replay ratio.

**Начинать с одного среза** бюджета 5k (три формы). Если лягут вплотную — плато не
сломано, сетку строить НИЖЕ, а не шире.

**Практический выхлоп.** Если плато начинается на ~200 донорах, это прямо лицензирует
якорение на внешнем пуле здоровых доноров (когда исходного трейна нет) — вопрос
«хватит ли 20 внешних доноров» становится точкой на измеренной кривой.

## RA: паддинг недостающих генов (РЕШЕНО, зафиксировать при сборке `build/ra_base.py`)

`scenarios/ra_padding_drift.py` — census-панель (3000 HVG) содержит 27 генов, которых

тяжело нагруженный вход дёргается из типичного значения в крайность, которую почти
никогда не видел на трейне.

**Фикс реализован** в `build/ra_base.py` — панель на выходе уже полная (3000 генов), MALAT1
вменён census-средним при сборке, остальные 26 занулены (безопасно, 0.065 < 0.27).

То есть примерно половина текущей панели — следствие ограничения по памяти, а не

**Следствие для пункта ниже:** метод, выбранный в плане (чанкованный аккумулятор вместо
`REDUCE_GENE_FRAC`), верен и является ГЛАВНОЙ частью фикса; смена 3000 → 8000 вторична
(покупает `STAT4` и запас). Снятие частотного порога при том же размере панели в 3000
уже возвращает 7 генов из 8. Заодно снят главный риск, записанный в том пункте
(«у здоровых дисперсия может быть near-zero, и никакой порог их не отберёт») — опровергнут
прямым замером.

**Известные блокеры/ограничения для того, кто будет это делать:**

Цепочка зависимостей пайплайна (для ТЕКУЩЕЙ 3000-генной базы): `build/census_healthy_base.py`
(`N_TOP_GENES=3000`, `REDUCE_GENE_FRAC=0.05`, захардкожено) → `build/train_census_scvi.py`
(число генов не важно, менять не нужно) → `build/lupus_cohort2_experiments.py` /
`build/lupus_cohortX_build.py --cohort 3.0|4.0` → `build/finetune_anchored.py --tag <tag>
--query-path ...` (общий, переиспользуется через `--tag`) → когортно-специфичный MMD-скрипт
(`finetune_mmd_phase2_earlystop.py` для c2, `finetune_mmd_earlystop.py --cohort-tag
lam30_cohort3` для c3, `finetune_mmd_phase2_cohort4_earlystop.py` для c4 — три отдельных
скрипта, не один общий) → `paper/encode.py --arms <...>` → `paper/{geometry,conservation,
neighbourhoods}.py --table/report all`.

Смена числа генов требует правки ТОЛЬКО `census_healthy_base.py` (сделать `N_TOP_GENES`
и шаг предварительного сокращения параметром, заменить шаг сокращения на чанкованный
аккумулятор) — весь даунстрим уже не зависит от числа генов и правок не требует, КРОМЕ
проверки, что `base_genes = BASE_HVG.var_names` в `lupus_cohort{2,X}_build.py` корректно
работает на 8000 генах (должно, но не проверено).

**Методологическая оговорка про чанкованный HVG**: `seurat_v3` во flavor scanpy не просто
ранжирует по сырой дисперсии/среднему — он подгоняет loess-кривую дисперсии от среднего по
всем генам в лог-пространстве, затем КЛИПИРУЕТ сырые per-cell counts каждого гена по
loess-предсказанному потолку перед пересчётом "стандартизованной дисперсии". Клипирование
трогает сырые per-cell значения, а не только сводки mean/var. Чистый одно-проходный
аккумулятор mean/var (что использовалось для RA-прокси в этой сессии) воспроизводит
ранжирование приблизительно, не точно. Точное воспроизведение требует двух проходов:
(1) накопить сырые mean/var, подогнать loess, получить потолок клипирования по гену,
(2) пересканировать данные с клипированием, накопить клипированную дисперсию. Решить явно,
достаточно ли приближённой одно-проходной версии, или стоит доплатить вторым проходом.

расширение бессмысленно. Опровергнуто: у здоровых доноров census `G0S2` — ранг 25 из 11288,

не зависит от числа генов, но ПУТЬ к базе — зависит, и он захардкожен в шести скриптах

`census_monocyte_supplement.py`, `lupus_cohortX_build.py`, `lupus_cohort2_experiments.py`,

`sceris.config.CENSUS_HVG`/`CENSUS_MODEL`, то есть переключается одной строкой в `.env`.
Две параллельные базы = либо перевести `build/` на `config`, либо править шесть констант.

**Две параллельные базы одновременно** (3000-генная, опубликованная; 8000-генная, новая)
означает удвоенный учёт — директории моделей, объединённые h5ad, состояния якоря — нужны
чёткие имена, чтобы не путать; существующая конвенция `--tag` в `finetune_anchored.py`
должна нести маркер размера базы (например, `lam30_cohort3_hvg8k`), а не переиспользовать
голые когортные теги.

Стандартные инфраструктурные правила (CLAUDE.md) без изменений применяются к любому новому
скрипту: чанкованное чтение через h5py только для файлов от 10GB+ с разбросанной маской,
запуск отдельным скриптом из терминала (никогда в кернеле ноутбука), проверка `journalctl -k
--since "-1 hour" | grep -i oom` перед тем, как считать молча убитую фоновую задачу багом кода.
