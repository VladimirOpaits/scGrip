## НЕИЗМЕНЯЕМОЕ ЯДРО ТЕКУЩЕГО МЕТОДА: healthy-reference MMD

**Replay Census никогда не является стороной MMD.** Его единственная роль — anchor:
сохранять исходную геометрию reference-модели на старых клетках. MMD — отдельная
MapQC-подобная сила: она сравнивает здоровые клетки новой когорты с независимой,
фиксированной выборкой здоровых Census (metric reference), которая не пересекается
ни с replay, ни с held-out Census. В рабочем split: healthy-A участвует в MMD,
healthy-B — независимая held-out проверка; ELBO считается только на healthy-A и
healthy-B, а больные клетки не входят ни в ELBO, ни в MMD и не дают градиент.

Интерпретация: ограниченные степени свободы LoRA/scArches должны выучить преобразование
counts→latent, которое убирает технический cohort/batch-сдвиг на здоровых. Затем то же
преобразование применяется к больным клеткам; оставшееся расстояние от здорового
reference-пространства — кандидат на disease/state signal, а не цель, которую MMD
должен схлопнуть. Не заменять это на MMD(replay, healthy-A) и не называть disease
остаток автоматически доказанным биомаркером: это рабочая гипотеза, требующая
независимой проверки.

**Новая архитектурная идея (адаптеры), причина**: `encode_covariates=False` означает у
энкодера НЕТ conditional-слота для нового батча вообще (colonка weight-матрицы для
batch one-hot никогда не существовала — не то что при `encode_covariates=True`, где для
нового батча просто добавляется новая нулевая колонка в уже существующую матрицу).
Вместо того чтобы переобучать базу с `encode_covariates=True` (это уже реализовано в
существующем публичном чекпойнте и в общем-то не даёт честного выигрыша для ГЕНУИННО НОВОГО
батча — его conditional-embedding всё равно стартует с нуля) — навешиваем on top новый
обучаемый модуль (Houlsby/LoRA-style adapter: `down: n_hidden→r`, `up: r→n_hidden`,
**`up` инициализирован нулём**, значит в момент t=0 `h' = h + up(σ(down(h))) = h`,
поведение идентично базовой модели) ПОСЛЕ каждого скрытого блока энкодера/декодера
(`n_hidden=128, n_layers=2` для нашей базы — не 500, это было у отклонённой публичной
модели). Backbone (все исходные веса) заморожен ПОЛНОСТЬЮ. Anchor теперь регуляризует
не весь latent, а именно выход адаптера: `λ·mean(‖adapter_out‖²)` только на клетках,
про которые точно известно, что они здоровые (новая когорта, control) — заставляет
адаптер быть ≈0 на здоровом подмногообразии, оставляя его свободным на больном (ELBO,
считаемый на ВСЕХ клетках, включая SLE/RA, даёт адаптеру стимул использовать эту свободу
для честной реконструкции реального батч+болезнь-сдвига). EWC в этой схеме избыточен,
если backbone не размораживается вообще — оставлен как уже выполненный baseline
(см. секцию EWC ниже), не встраивается в адаптерную архитектуру. Место вставки — ПОСЛЕ
скрытого блока (128-мерная активация до финальной проекции 128→20), а не только на
самом `z` (50/20-мерный битлнек мог уже стереть тонкий сигнал раньше, чем адаптер
на z успеет его увидеть).

Repulsion/margin-term для явного отталкивания больных клеток (идея: калибровать порог
по MMD между двумя независимыми здоровыми когортами, а не произвольным числом) —
обсуждён, отложен до готовности attract-only (anchor-на-адаптере) версии.

Восстановление IFN-сигнатуры в найденных генах — ПОЛОЖИТЕЛЬНЫЙ КОНТРОЛЬ, не валидация. r(IFN, расстояние) на донорском уровне уже 0.85, поэтому появление ISG в DE есть арифметическое следствие известной корреляции, а не новая информация. DE между клетками с высоким и низким attention циклична — считать псевдобалком на донорском уровне.

Композиция в классификаторе — НЕ конкатенацией, а подогнанным первым nuisance-offset (CLR): `logit(y) = offset(композиция) + w · attention_pool(клетки)`. Иначе композиция (0.985 в одиночку) почти удовлетворяет BCE, attention не получает градиента, и «в каких клетках» теряется. Softmax-attention даёт взвешенное СРЕДНЕЕ, то есть дескриптор состояния, структурно слепой к численности — композиция комплементарна и выброшена самим пулингом.

Инфраструктурные ограничения этой машины (14GB RAM, GPU 6GB):

- Тяжёлая предобработка (subset/HVG/scVI-подготовка на файлах масштаба 10GB+) — ТОЛЬКО отдельным скриптом (`python build/...py` из терминала), никогда в Jupyter-кернеле внутри VS Code. Повторные попытки в ноутбуке при падении копят память между запусками и один раз реально уронили весь VS Code.
- Subset backed AnnData (`adata[mask].copy(filename=...)`) на файле от ~10GB c РАЗБРОСАННОЙ (не подряд идущей) булевой маской — НЕ memory-bounded в anndata, надёжно роняет OOM-killer (подтверждено дважды через `journalctl -k`, ~12GB anon-rss каждый раз, killed on the subset line). Для непрерывного блока (одна когорта подряд) обычно проходит, для маски из нескольких разбросанных когорт/групп — нет.
  - Фикс: читать `raw.X` вручную через `h5py` чанками по строкам (~50k), фильтровать маской внутри чанка, копить только отобранные (уже маленькие) строки — см. `build/lupus_base.py::_chunked_masked_read`. Память ограничена размером чанка, а не размером файла или разбросанностью маски.
- В CELLxGENE-style h5ad (`feature_is_filtered`, `schema_version`, `citation` в obs/var/uns) — `adata.X` часто уже z-scaled/clipped (отрицательные значения, потолок ~10.0), НЕ сырые counts. Сырые integer counts — в `adata.raw.X` (полный ген-панель). Перед любым scVI/HVG на новом файле такого типа — сверять `X.min()`/`X.max()`/`np.allclose(X, round(X))`, а не полагаться на форму объекта.
- Долгие фоновые процессы гибнут при перезапуске/потере сессии Claude Code без явного маркера падения (`[killed]` в логе без причины) — при таком выводе сначала проверять `journalctl -k --since "-1 hour" | grep -i oom`, прежде чем чинить код: часто это не баг скрипта, а OOM-killer.
